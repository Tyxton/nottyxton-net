>> DEPLOYING_UNPOLLER

[ DOCKER ]

Deploying unpoller is rather simple, all you need to do is point it at your gateway with a created user and it starts scraping immediately. 

  unpoller:
    image: ghcr.io/unpoller/unpoller:latest
    container_name: monitoring-unpoller
    restart: unless-stopped
    networks:
      - core-itim   # easy to refer with a common name http://monitoring-unpoller:9130
    environment:
      - UP_UNIFI_DEFAULT_URL=${GW_URL}          # e.g. 192.168.1.1
      - UP_UNIFI_DEFAULT_USER=${UNIFI_USER}     # Create an Admin user for Unpoller to Auth
      - UP_UNIFI_DEFAULT_PASS=${UNIFI_PASS}     # Create a password for it
      - UP_UNIFI_DEFAULT_VERIFY_SSL=false       
      - UP_PROMETHEUS_HTTP_LISTEN=0.0.0.0:9130 
      - UP_INFLUXDB_DISABLE=true
    ports:
      - "9130:9130"

[ SCRAPING ]

This is made pretty simple as well, you can create an Prometheus scrape directly, or in my case Grafana Alloy. 

  // Unifi Unpoller Scraping
  prometheus.scrape "unpoller" {
      targets         = [{"__address__" = "monitoring-unpoller:9130"}]
      forward_to      = [prometheus.remote_write.default.receiver]
      job_name        = "unifi/network"
      scrape_interval = "30s"
  }

Unpoller was one of if not the easiest to setup in my monitoring stack because it's so straight forward. At some point I may write a custom relabel rule for it, though I don't deem it necessary at all.

>> PVE_OTEL

[ EXPORTING ]

This was almost as simple as Unpoller, though I did create a dedicated LXC to scrape Raiden's logs. For the OpenTelemetry export, you simply go to the Proxmox Web UI -> Datacenter -> Metric Server. Point it to your collecting alloy instance and port, disable Verify SSL, and make sure it is enabled.

The logs were more involved in my case. Introduced into the MSF suite is ops-itim-01, a sister node to ops-core-01. Its sole purpose is to collect and export PVE logs and metrics. The reason I setup a dedicated LXC for this was largely for isolation and damage control, an island with secure information is easier to protect than a metropolitan area, it's also one less thing running on the hypervisor - which I always try to avoid, and it takes the load off of ops-core-01's alloy instance to parse and normalize an extra set of logs. As additional mount points I added: 

  mp0: /var/log,mp=/mnt/host/log,ro=1,backup=0
  mp1: /var/log/journal,mp=/mnt/host/log/journal,ro=1,backup=0

This gives the container access to the host's logs, ro=1 is extremely important here, you don't want the container to have write access to host logs. Not that alloy tampers with it anyways, it's best practice.

[ INGESTING ]

The alloy instance ingesting the metrics and logs needs two unique blocks on top of it's own collection. 

// ------------------------------ //
//  PROXMOX METRICS (ops-itim-01) //
// ------------------------------ //

otelcol.receiver.otlp "pve_receiver" {
    http {
        endpoint = "0.0.0.0:4318"
    }
    grpc {
        endpoint = "0.0.0.0:4317"
    }

    output {
        metrics = [otelcol.processor.transform.pve_normalize.input]
    }
}

otelcol.processor.transform "pve_normalize" {
    error_mode = "ignore"
    
    output {
        metrics = [otelcol.exporter.prometheus.to_prometheus.input]
    }
}

otelcol.exporter.prometheus "to_prometheus" {
    forward_to = [prometheus.relabel.pve_host_override.receiver]
}

prometheus.relabel "pve_host_override" {
    forward_to = [prometheus.remote_write.default.receiver]

    rule {
        target_label = "instance"
        replacement  = "raiden"
    }

    rule {
        target_label = "nodename"
        replacement  = "raiden"
    }

    rule {
        target_label = "Hostname"
        replacement  = "raiden"
    }
}

>> TRUENAS_GRAPHITE

[ EXPORTING ]

This is one of the least graceful setups in the monitoring stack, I will be the first to admit that a lot of times it feels less like an integration and more like a workaround. Nonetheless, you can find the "Reporting Exporters" via TrueNAS Web UI -> Reporting -> Exporters. There you can configure your Graphite export.

  • [ Type ] GRAPHITE - Unfortunately, it's your only choice natively.
  • [ Prefix ] defaults to truenas.
  • [ Namespace ] I recommend setting this to the hostname of your system.
  • [ Send Names Instead of IDs ] I recommend checking this for easy identification.
  • [ Matching Charts ] * - Capture Everything

[ INGESTING ]

You then need to setup a graphite receiver, in my case it's a docker container. 

graphite-exporter:
    image: prom/graphite-exporter:latest
    container_name: monitoring-graphite
    restart: unless-stopped
    ports:
      - "2003:2003/tcp"  # Where the metrics get pushed to
      - "2003:2003/udp"  
      - "9108:9108"      # The port alloy will scrape
    networks:
      - core-itim
    volumes:
      - ${DOCKER_DIR}/graphite/graphite_mapping.conf:/etc/graphite-exporter/graphite_mapping.conf
    command:
      - "--graphite.mapping-config=/etc/graphite-exporter/graphite_mapping.conf"
      - "--graphite.listen-address=:2003"
      - "--web.listen-address=:9108"

You then need to set up your graphite_mapping config, mine looks like this: 

mappings:
- match: "msf.motherbase.*.net.*.*"
  name: "truenas_network_traffic_bytes"
  labels:
    host: "$1"
    interface: "$2"
    direction: "$3"

- match: "msf.motherbase.*.cpu.usage.*"
  name: "truenas_cpu_usage_percent"
  labels:
    host: "$1"
    core: "all"
    type: "$2"

# Broad ZFS Matcher
- match: "msf.motherbase.*.zfs.*.*"
  name: "truenas_zfs_stat"
  labels:
    host: "$1"
    pool: "$2"
    metric: "$3"

# Broad Dataset Matcher
- match: "msf.motherbase.*.dataset.*.*.*"
  name: "truenas_dataset_stat"
  labels:
    host: "$1"
    pool: "$2"
    dataset: "$3"
    metric: "$4"

# Catch-all for everything else to keep the 'msf' prefix clean
- match: "msf.motherbase.*.*.*"
  name: "truenas_${2}_${3}"
  labels:
    host: "$1"

I would not recommend using the above config. To be completely transparent, it doesn't seem to work at all and instead pushes all of the raw metrics straight through. I am actively working on this, though.

[ CUSTOM_ZFS_EXPORT ]

#!/bin/bash
# ZFS Export Metrics Bridge
# Pushes the logical pool data to the graphite exporter

TARGET_IP="10.20.0.50"
TARGET_PORT="2003"
PREFIX="msf.motherbase.truenas.zfs.pool"
TIMESTAMP=$(date +%s)

for pool in kazuhira ocelot meiling; do
        cap=$(zpool list -H -o capacity $pool | tr -d '%')
        health_raw=$(zpool list -H -o health $pool)
        [ "$health_raw" == "ONLINE" ] && health=1 || health=0

        echo "$PREFIX.$pool.capacity $cap $TIMESTAMP" > /dev/udp/$TARGET_IP/$TARGET_PORT
        echo "$PREFIX.$pool.health $health $TIMESTAMP" > /dev/udp/$TARGET_IP/$TARGET_PORT
done

I wrote this custom bridge I think about 2 years ago. I have it triggered via cronjob every minute. This wraps up the local ZFS pool data and ships it via UDP to the graphite container. It's setup to be fire-and-forget, if the container ever goes down the cronjob won't exit and fail.

The main reason I wrote this bridge script was because TrueNAS does not natively export a binary health indicator, nor capacity of each pool.This simple script allows be to have a better naming convention, granular control of the metrics, and more simple querying.

[ ARC_HIT_RATIO ]

(truenas_ddhit_ddhit{instance=~"$truenas_nodes"} + truenas_dmhit_dmhit{instance=~"$truenas_nodes"})
/ (truenas_ddhit_ddhit{instance=~"$truenas_nodes"} + truenas_dmhit_dmhit{instance=~"$truenas_nodes"} + truenas_ddmis_ddmis{instance=~"$truenas_nodes"})

Similar to above, this gives you the percentage of hits to misses. Generally speaking you want this to stay above 90%, otherwise your disks are being spun up too often, below 80-90% I would look into increasing your RAM or adding a dedicated LARC Cache.

[ MEMORY_ALLOCATION ]

truenas_total_total{instance=~"$truenas_nodes"}

truenas_available_available{instance=~"$truenas_nodes"}

truenas_avail_avail{instance=~"$truenas_nodes"}

This was a major pain, thanks to the unusual naming convention it look a lot of hunting and eventually using Ctrl+F in the raw graphite export to read the HELP/TYPE notes to figure out where these metrics were and what their name was. total_total is Total Memory, available_available is the Available Memory to the system, avail_avail is the memory used by ARC.

>> INGEST_AGGREGATION

[ SPLIT_SETUP ]

Because I have so many nodes, I have ops-core-01 acting as a fleet aggregator, it collects all of the metrics to one point. If you have a similar setup, the above won't work properly - or at least fully. You need to add the actual discovery and scrape rules for each, in my case: 

// ---------------------------------- //
//  FLEET SCRAPING (AGGREGATOR ONLY)  //
// ---------------------------------- //

discovery.relabel "fleet_base" {
    targets = [
    {% for host in groups['prom_endpoint'] | default([]) %}
        { "__address__" = "{{ hostvars[host].ansible_host | default(host) }}:9100", "instance" = "{{ host }}" },
    {% endfor %}
    ]
}

// Node Exporter Fleet Scraping
prometheus.scrape "node_exporter_fleet" {
    targets         = discovery.relabel.fleet_base.output
    forward_to      = [prometheus.remote_write.default.receiver]
    job_name        = "node-exporter"
    scrape_interval = "15s"
}

// cAdvisor Fleet Relabeling (Maps 9100 node-exporter port to 8080 cAdvisor port)
discovery.relabel "cadvisor_targets" {
    targets = discovery.relabel.fleet_base.output
    rule {
        source_labels = ["__address__"]
        regex         = "(.*):9100"
        replacement   = "$1:8080"
        target_label  = "__address__"
    }
}

prometheus.scrape "cadvisor_fleet" {
    targets         = discovery.relabel.cadvisor_targets.output
    forward_to      = [prometheus.remote_write.default.receiver]
    job_name        = "cadvisor"
    scrape_interval = "30s"
}

This is Jinja2 templating, you would need to map the individual IP addresses of each node if not using Ansible, and same each instance accordingly. The regex relabel rule makes it simple to reuse the same discovery rule and just remap the cadvisor listener, this way you don't have to rewrite the whole list twice.

[ GLOBAL_NORMALIZATION ]

Since Alloy collects so many different kinds of logs, from near endless sources, I needed a robust solution that cleaned everything on a non-granular level. It's made to handle Docker Container, Systemd, and Syslog uniformly so that all data looks the same for easy lookups, queries, etc. 

loki.process "fleet_logs" {
  forward_to = [loki.write.default.receiver]

  stage.json {
    expressions = {
      extracted_level = "level",
      severity        = "severity",
      json_message    = "log",
    }
  }

  // Fallback regex for standard log levels (non-greedy, word-bounded)
  // Encountered a specific behaviour in Unifi Unpoller where this log:
  // XXXX/XX/XX XX:XX:XX [INFO] UniFi Measurements Exported... Err: 0 ...
  // Would map it as an ERROR because it would catch `Err:` before the INFO.
  stage.regex {
    expression = "(?i).*?\\b(?P<fallback_level>CRITICAL|FATAL|ERROR|WARN(?:ING)?|INFO|DEBUG|NOTICE|TRACE)\\b"
  }

  // Consolidate log level hierarchy
  stage.template {
    source   = "working_level"
    template = "{% raw %}{{ if .extracted_level }}{{ .extracted_level }}{{ else if .severity }}{{ .severity }}{{ else if .fallback_level }}{{ .fallback_level }}{{ else if .level }}{{ .level }}{{ else }}info{{ end }}{% endraw %}"
  }

  // Lowercase collation
  stage.template {
    source   = "working_level"
    template = "{% raw %}{{ .working_level | lower }}{% endraw %}"
  }

  stage.replace {
    source     = "working_level"
    expression = "err|crit|fatal|panic|error"
    replace    = "error"
  }

  stage.replace {
    source     = "working_level"
    expression = "warn|warning"
    replace    = "warn"
  }
  
  stage.replace {
    source     = "working_level"
    expression = "info|information|debug|notice"
    replace    = "info"
  }

  // Finalize labels
  stage.labels {
    values = {
      level             = "working_level",
      unit              = "unit",
      syslog_identifier = "__journal__syslog_identifier",
    }
  }

  // Clean output formatting
  stage.template {
    source   = "message"
    template = "{% raw %}{{ if .json_message }}{{ .json_message }}{{ else }}{{ .Entry }}{{ end }}{% endraw %}"
  }
}

This happens in a couple of stages. First, our pipeline tries to extract clean JSON. If it fails, it falls back to standard regex processing for plaintext logs.

I had to refactor the original regex expression because it was "greedy", what that means is that it reads the line right to left, on top of that it wasn't word bounded; If it found "ERR" it would mark it as ERROR, which is good, however it would also flag OVERRIDE, PREFERRED, etc. I had a specific edge case with Unifi Unpoller, which to my knowledge are the only lines that exhibited this; however this change is a major improvement as any container, host, etc could have been mislabeled at any point. The specific log I noticed this in was: `XXXX/XX/XX XX:XX:XX [INFO] UniFi Measurements Exported... Err: 0 ...`. As we can see, it clearly says INFO, but because it was greedy it caught the "Err" first, marking it as an error.

After that, it creates a hierarchy, going from JSON -> SEVERITY (From JSON/Syslog) -> FALLBACK_LEVEL (from our regex) -> any existing level variable -> if it finds nothing, it labels it as INFO. Then, it normalizes everything to lowercase for the next step (ERR become err). Then it collates dozens of different log flags into unified conventions. err|crit|critical|panic|error all become error, so on. Then, it indexes these fields into loki labels so that it's queryable. Lastly, if it was a long JSON string, it unwraps it to read just the "log:" otherwise it gives the standard .Entry.

sum by (instance, container) (
  count_over_time(
    {instance=~"$nodes"} 
    | logfmt
    | container!=""

If you wanted just the instance itself, you would drop the container variables.

[ TRAILING_LOGS ]

{instance=~"$nodes|$pve_nodes|$truenas_nodes"} | logfmt | level=~"(?i)error" | keep instance, container, level, line

This displays all logs, that match a case-insensitive error. This is particularly nice because normally "Unique Labels" in Grafana matches absolutely everything attached, but with the keep rule, we get to pick and choose. For the case of this line we want the instance and container pinned to each log line. You always want to keep level and line since it enables [LEVEL]: Log parsing.
